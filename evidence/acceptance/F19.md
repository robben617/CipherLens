## 1. 答错：1 格 error + propagated 数量 downstream

真实后端提交（第 7 个字节 `fb → fa`）原始响应：

```json
{
  "summary": { "total_bytes": 16, "wrong_count": 1 },
  "first_diff": {
    "step_index": 39,
    "round": 10,
    "step": "add_round_key",
    "byte_index": 7,
    "expected": 251,
    "actual": 250
  },
  "propagated": [8, 9, 10, 11, 12, 13, 14, 15],
  "input_mismatch": null,
  "expected_ciphertext": "3925841d02dc09fbdc118597196a0b32"
}
```

| 断言 | 实测 |
|---|---|
| `.is-error` 数量 | **1** |
| `propagated.length` | **8** |
| `.is-downstream` 数量 | **8** |
| 是否相等 | **true** |
| 受污染字节下标 | `8,9,10,11,12,13,14,15` |
| 0–6 号字节 | 不在 propagated 内，**不灰化**（不自行扩大范围） |
| `is-error` 是否用于 downstream | **否**（独立选择器） |

截图：`evidence/acceptance/F19-real.png`（69,042 B）。

> 手册导语写“只标 1 格红、其余灰化”。“其余”由后端 `propagated` 唯一决定；本次是 8 个下游字节，不是 15 个。前端没有推算未返回的字节，避免制造第二套传播语义。

**真实后端路径**：

| 项 | 实测 |
|---|---|

| 跳转 URL | `/workbench?step=40&byte=7` |

截图：`F19-workbench-grading.png`（41,290 B）。

> **文档口径冲突（需评审知悉）**：手册验收第 2 条写“第 4 轮 列混合 字节 7”，但 B3 判分契约只接收最终密文，没有学生中间态，后端无法反推首次分叉发生在哪一轮。当前后端按“末步 39 的 AddRoundKey”给出可复现位置，因此真实路径显示“第 10 轮 轮密钥加”。前端不做任何推算；“第 4 轮 列混合 字节 7”的文案映射由契约样例响应验证（`?debug=quiz`），不是真实后端返回值。该差异与 B3 证据一致，未改后端。

## 3. 判分期 key 左竖条

真实后端路径、工作台第 40 步（trace `steps[39]`）：

| 项 | 实测 |
|---|---|
| 当前步 `key_indices` | `[0..15]`（后端 trace 实测 16 个） |
| `.is-key` 数量 | **16** |
| 每个 key 格是否有左竖条 | **是**（`.c-byte.is-key` 的 `inset 3px` 左竖条） |
| 同一矩阵上 error / downstream 是否同时存在 | 1 / 8 |
| `.is-error` 表现 | 底色 `oklch(0.545 0.195 27 / 0.1)`（红 10%）；右下折角 **1**、`≠` **1** |
| `.is-downstream` 表现 | 底色 `oklch(0.945 0.004 250)`（灰化）；折角 **0**、`≠` **0** |
| error 组合阴影 | error 底条 + **3px key 左竖条**（`inset 3px 0 0`） |
| key 组合阴影 | **3px key 左竖条**（`inset 3px 0 0`） |

> 追加修复：`.is-key` 原本会覆盖 `is-error` / `is-downstream` 的底色（同类选择器顺序在后）。已补 `.is-error.is-key` 与 `.is-downstream.is-key` 组合态：判分底色/边框/折角归 error 或 downstream，key 只保留 45° 斜纹与左竖条。`is-changed` 在判分期仍整体让位。

截图：`F19-workbench-grading.png`。

> **第二处文档口径冲突**：手册写“哪 8 个密钥字节参与异或”，但 AES-128 末步 AddRoundKey 的 `key_indices` 实际是 16 个（后端 trace 与 B1/B2 数据一致）。前端按真实 `key_indices` 挂 16 个左竖条，不写死 8。若评审要求 8，需要先修订算法/数据口径，不能在前端截断。

`paintFor()` 同时输出 `is-error`、`is-downstream`、`is-key`，并保证 `is-changed` 在判分期整体让位；`key` 不参与让位。

## 4. 输入非法字符：不计入分母

把明文第 7 个字符 `a` 改为 `G` 后提交，后端原始响应：

```json
{
  "summary": { "total_bytes": 0, "wrong_count": 0 },
  "first_diff": null,
  "propagated": [],
  "input_mismatch": { "field": "plaintext", "char_index": 6, "expected": "hex" },
  "expected_ciphertext": ""
}
```

| 项 | 实测 |
|---|---|
| 页面文案 | **`明文的第 7 个字符不是十六进制数（你写的是 G）`** |
| `counted` | **false** |
| 会话统计（前 → 后） | `done 0 / correct 0` → **`done 0 / correct 0`** |
| `.is-error` 数量 | **0**（输入错误不画成算法错误） |
| `first_diff` 分支 | 不进入（不显示定位矩阵） |

截图：`F19-input-mismatch.png`（51,019 B）。

> 手册要求“贴记录页前后对比”，但 `RecordsView` 属于 F20，当前仍是标题占位页。本轮用 store 的会话统计前后值（`data-stats`）代替记录页对比，并在 F20 接记录页后回归。

## 6. 判分叠加与 step 绑定

跳转后在目标步显示叠加，切步后整体撤场：

| 时刻 | 当前步 | error | downstream | key |
|---|---|---|---|---|
| 跳转落点（契约样例） | 16 | 1 | 8 | 0（该步 mix_columns 无 key） |
| 切到第 39 步后 | 39 | **0** | **0** | **0** |
| 跳转落点（真实后端） | 40 | 1 | 8 | 16 |
| 切到第 39 步后 | 39 | **0** | **0** | **0** |

截图：`F19-step-cleared.png`（30,263 B）。

实现方式：`MatrixStage` 的 `grading` 只在 `overlayArmed && currentStep === first_diff.step_index + 1 && !input_mismatch` 时为真；离开该步时调用 `disarmOverlay()` + `clearPaint()`，不把某一步的错画到另一步。

## 10. 已知边界

| 项 | 说明 |
|---|---|
| 定位位置口径 | 真实后端返回末步 `round 10 / add_round_key`；手册示例“第 4 轮 列混合”由契约样例响应验证，不是算法反推 |
| key 字节数 | 按后端 `key_indices` 挂 16 个；手册写 8，属于文档与 AES-128 末步不符 |
| 统计范围 | `stats` 只在当前页面会话内累积；刷新即重置，持久化与记录页留给 F20 |
| 输入不一致的记录页对比 | `RecordsView` 仍是 F20 占位页，本轮用会话统计前后值代替 |
| `?debug=quiz` | 临时验收入口，暴露 `window.__quiz`（contract/missing/submit/setField）；W4 清理 |
| 判分叠加的生命周期 | 仅“在工作台对照”跳转后 armed；切步即撤场；直接打开工作台不会自动叠加 |
| 整段错版式 | 已支持四角括 + 固定「影响范围：16 字节」，但本轮回后端不会返回 `step_index=0 && propagated.length=16` 的样例，版式未单独截图 |
| 题库 | 当前只有 1 道内置题（`q_042`，标准向量），题库接口与选题策略未做 || 验收启动地址 | 本轮实测 Vite 默认只绑 `localhost`（IPv6），`http://127.0.0.1:5175` 返回 000；启动必须加 `--host 127.0.0.1`（或验收脚本改用 `localhost`） |
| 服务生命周期 | 沙箱内后台 dev server/uvicorn 会随命令结束被回收；验收需在同一条命令内“启动 → 采集 → 结束”，或使用跨命令存活进程 |
